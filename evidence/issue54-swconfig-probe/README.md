Ucode base `11a53fd8e911573860950ee8e549b337a8742438`, CodeQL 2.27.4, 2026-11-23. This is an evidence-only probe, not a new production model or security finding. The retained .ql files were temporarily placed in `ql/src/extractor-smoke` for execution and then removed. The issue #54 guard against unsupported path claims remains in force.

## Question and source-first controls

Can current DataFlow represent a source-to-popen command path for the two real swconfig uses, without asserting unknown helper behavior? Before execution, the expected source-level cases in `controls.uc` were: direct has a command-input dependency; fixed does not; reassignment and shadow use fixed values, so have no dependency from the earlier source on these straight-line executions; unknown helper has an argument dependency but its return dependency is unknown. These are fixture expectations, not claims of general runtime coverage. All use the same imported `popen`, method shape and `request.args.cmd` source. Inventory independently checks those gates for every case. No branch or wrapper causes a negative to fail an earlier selection gate; shadow uses a nested lexical block intentionally.

Fresh extraction selected `controls.uc` (SHA-256 `66955ab7f10b3ce0dec62cf506ab3347e7f0bf27769909e3c25cec2a2d14a8d7`); diagnostic rows identify exactly that file and no extraction errors. The retained inventory has all five full source and sink locations. `Issue54ControlProbe.json` shows current Models relation returns direct, reassignment, shadow and unknown, but not fixed. It correctly distinguishes fixed from direct while not distinguishing reassignment or lexical shadowing. Unknown is reported by syntactic containment, which does not establish return dependency or quoting semantics. No separate mutation run was performed. No candidate flow implementation is asserted or tested; these controls measure the existing syntactic relation, and thus cannot prove behavior of a future one.

The extractor pack was reused from `/private/tmp/openwrt-typed-handoff-live-20261123/extractor-pack`, binary SHA-256 `2ff17b40e4abdacb6463148675b23874cf3badcf11c9c682c04218d5f7fbeca1`; no rebuild or source-to-binary attestation claimed. Database init/index/finalize commands are in the corresponding logs; `commands.json` contains query commands and exit status, with decode output and stderr retained. The only source was the control file. Warnings include qlpack commit hash retrieval and disabled query-stage caching; commands exited zero. The two execution-specific command files retain actual paths; these must be adjusted for replay.

## Real sites and blocker

`Issue54AstWitness` reports exact AST identities for request.args.switch nested as shellquote's first argument, nested in each popen argument, at lines 343 and 400. This is a syntax witness, not an edge through the helper or proof of its target. `Issue54TemplateInventory` reports exactly the two concrete templates at 343 and 400 and `no ExprNode` for each. Its negation is guarded by positive template enumeration, so empty extraction cannot explain the result. `Issue54TemplateNodeProbe` separately produced zero rows. These were queries on the prior single-file database `/private/tmp/issue54-query-comparison/database`, not fresh extraction. The prior receipt `extracted.csv` and companion `prior-extraction-commands.json` are retained from the independent assessment, which reports no extraction errors and selected only `usr/share/rpcd/ucode/luci`, source SHA-256 `6f9d972958d9cfb8a7ba421f38f0a5b03718ffeb0e30d460b64c9faf725fc54e`, LuCI revision `b2e0be4b46ec0fd43394c081fa7c50657af14011`. See `docs/evidence/issue-54-candidate-assessment.md` on branch `evidence/issue-54-assessment` for provenance and qualifications.

The inventory was run with the same argv as `ast-command.json`, replacing its query and output paths with `Issue54TemplateInventory.ql` and `/private/tmp/issue54-query-comparison/Issue54TemplateInventory.bqrs`; it exited 0 and was decoded as JSON with `--entities=url,string`. `Issue54TemplateNodeProbe` ran likewise and produced only the CSV header. Both had the same warnings as the other queries. AST witness output is `Issue54AstWitness.json`. The baseline Models predicate is in `ql/lib/codeql/ucode/m3/Models.qll`; it uses recursive containment and same-function name binding rather than SSA and is not a path graph. `TaintTrackingPrivate.qll` adds no default taint steps to `localFlowStep`. Existing `docs/m4-template-string-call-arguments.md` independently documents that whole templates are CFG nodes but not DataFlow expression nodes.

The smallest named prerequisite for an actual DataFlow path ending at these command arguments is a reviewed representation for the constructed template value, with justified interpolation/construction propagation and controls. A separately justified model or explicitly labeled unknown boundary is needed for shellquote argument-to-return dependency: merely nesting it in the AST cannot establish this edge. A test-only AST witness can display nesting today, but cannot honestly claim a complete value path. A future candidate must produce an observable path through those boundaries and distinguish the control reassignment and shadow cases, while retaining fixed and unknown as appropriate; its consumer contract and independent acceptance remain separate gates. This probe does not establish that a novel bounded path representation is impossible, only that the current DataFlow node/edge substrate and existing Models relation do not supply this path.
