# Ucode UCI write inventory at the LuCI profile pin

This is a bounded source audit, not a sink model, a security finding, or proof of a runtime write. The `luci-ssl-25.12` profile in codeql-openwrt records LuCI at `b2e0be4b46ec0fd43394c081fa7c50657af14011`; its `corpus/lock.json` SHA-256 is `b4cbdabb76df90a807aba7d42ae675198c7b7b09c3b84db259a3a4c941b0ea9a`. The routing report (`reports/m4-luci-ssl-files.json`, SHA-256 `05598b6bb1dd7d63a4f8cc109367980e51f334385704c3d92453b411c737ab9c`) names ten plain entries, twelve markup entries, and two uncertain entries. The generated `version.uc` entry is represented by a Makefile, not a checked-in ucode file. This audit inspected the other nine plain source paths from that report, at the pinned tree. It does not cover all OpenWrt packages, JavaScript, markup, generated code, or alias/dynamic dispatch exhaustively. The report itself is a transcribed install inventory, not a live build.

## Candidate

[LuCI controller `uci.uc`:79](https://github.com/openwrt/luci/blob/b2e0be4b46ec0fd43394c081fa7c50657af14011/modules/luci-base/ucode/controller/admin/uci.uc#L76-L85), installed as `/usr/share/ucode/luci/controller/admin/uci.uc`, calls `ubus_call('uci', 'commit', { ubus_rpc_session: ctx.authsession, config })` for each config returned by `changes`. The local helper [lines 25–32](https://github.com/openwrt/luci/blob/b2e0be4b46ec0fd43394c081fa7c50657af14011/modules/luci-base/ucode/controller/admin/uci.uc#L25-L32) forwards its arguments to `ubus.call(object, method, args)`. This is a concrete indirect request to the UCI ubus `commit` method; successful persistence, reachability, authorization and effects are not established here. The source blob is `c38a42b10bfefbaa31741feae9395abd8a1f8e40`, SHA-256 `ac75cfef7d74f87ed7f957778004a7bf486c76df699398c215795b4947e0c93e`.

This call is **not** a `cursor().set`, `.commit`, or `.delete` call. The direct cursor-write criterion in issue #53 remains unmet by this inventory. The pinned rpcd plugin and `runtime.uc` and `dispatcher.uc` use cursor reads; a text search of the nine plain sources for method names `set`, `commit`, `delete`, `save`, `add`, `rename`, `set_list`, and `delete_all` found only `runtime.uc:54` (`this.L.set`, a different receiver). That search is a candidate census, not a proof about indirect, computed, or differently named operations. The controller also calls UCI `apply` at lines 50 and 82, `confirm` at 108, and `revert` at 145; these are distinct operations, and `changes` at 76 and 144 is a read. `ubus.call('session', 'set', ...)` at 59 is a session operation, not UCI `set`.

## Proposed controls before any model

For a separately scoped indirect-ubus inventory, first extract the actual pinned controller and assert the exact call at line 79, its literal object/method arguments, the object argument, and the forwarding call at line 28. Require exact file identities and empty extraction-error diagnostics; a path match alone is insufficient. An isolated positive control should retain the local helper forwarding `('uci', 'commit', args)`. Discriminating negatives should include `('uci', 'changes', args)`, `('session', 'set', args)`, a different local function named `ubus_call`, a property read without a call, and a direct `ubus.call` with unknown object or method. If the intended family requires direct cursor writes instead, use a separate synthetic `cursor().commit(...)` positive and `cursor().get(...)` plus unrelated `.commit(...)` negatives; synthetic controls do not establish a real pinned call. Assertions should check exact locations and argument positions, not counts alone. Model semantics and alias/binding resolution require their own review.

Reproduce the source census by checking out the recorded LuCI SHA and selecting the nine existing source files classified `plain` by the recorded routing report (excluding its generated Makefile entry). Search both literal UCI ubus operations and cursor/write method names, then inspect each result and the helper body. A broader search or a different profile may find other candidates; this result is limited to the listed files and the stated search shapes.

A second inspection using `String.getString()` returned `uci` and `commit` for the first two line-79 positions. Results included multiple AST entities at identical locations, so these observations are not a uniqueness gate. They establish that argument nodes are present, not that the wrapper's binding, forwarding flow, or UCI semantics are modeled. The exact call relationship and discriminating negatives above remain future gates.
